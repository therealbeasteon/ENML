# M0.10 ARM64 Validation

M0.10 closes the first implementation track by proving that the M0 userspace design is not accidentally tied to x86-64 native layout or host-only build assumptions.

## Two independent ARM64 gates

The repository carries two CI paths:

1. **Native AArch64 Linux** on GitHub's `ubuntu-24.04-arm` runner. It configures the ordinary `host-debug` build on an actual AArch64 VM, builds the complete M0 tree, and runs the complete CTest suite. This is the authoritative M0.10 runtime gate for architecture-sensitive Linux behavior such as process credentials, descriptor passing, pidfds, service restart, seccomp, rlimits, and the supervised service path.
2. **x86-64 → AArch64 cross build** using `g++-aarch64-linux-gnu`, plus `qemu-aarch64` for user-mode-safe tests. This independently proves the repository can be cross-compiled from the normal developer host and that build-time OSIDL generation uses a native host tool instead of trying to execute a target-architecture generator.

The QEMU-user path intentionally excludes supervisor/sandbox tests. User-mode emulation is useful for codec, IPC and ordinary process tests, but it is not treated as equivalent evidence for target-kernel seccomp/service-exec behavior. Those properties are exercised by the native AArch64 job.

## Host-tool separation

`interfaces/echo/CMakeLists.txt` now distinguishes build and target machines. Native builds use the in-tree `$<TARGET_FILE:osidlc>`. Cross builds require `EMNL_OSIDLC_EXECUTABLE` to name an absolute host executable. The `host-tools` preset builds that executable first; the `arm64-debug` preset then consumes it while producing AArch64 libraries/services/tests.

This avoids a classic cross-build error: compiling `osidlc` for AArch64 and attempting to execute that AArch64 binary on the x86-64 build host during code generation.

## AArch64 runtime probe

`arm64_runtime_probe_test` only compiles when the target processor is AArch64. It has a compile-time `__aarch64__` requirement and verifies at runtime that:

- pointers are 64-bit,
- `WireHeaderV1` produces the exact same 40 golden bytes as the x86-64 build,
- the wire representation therefore remains explicit little-endian data rather than C++ native layout,
- `SOCK_SEQPACKET` works from the AArch64 executable,
- one `SCM_RIGHTS` descriptor crosses the channel,
- the received descriptor is `FD_CLOEXEC`,
- `SCM_CREDENTIALS` identifies the actual packet sender,
- the transferred descriptor remains a usable kernel object.

Existing unit/integration tests provide broader coverage; the probe exists to make the architecture gate explicit rather than infer it from a successful compile.

## Reproduction commands

On an x86-64 Debian/Ubuntu host with `g++-aarch64-linux-gnu` and `qemu-user` installed:

```sh
cmake --preset host-tools
cmake --build --preset host-tools --target osidlc

cmake --preset arm64-debug
cmake --build --preset arm64-debug
ctest --preset arm64-debug --output-on-failure \
  -E 'supervisor_|sandbox_landlock_test'
```

On a native AArch64 Linux host:

```sh
cmake --preset host-debug
cmake --build --preset host-debug
ctest --preset host-debug --output-on-failure
```

## Evidence rule

A cross-compile alone is not a runtime pass. QEMU user mode is not a substitute for native kernel evidence. M0.10 is complete only when CI records a successful native AArch64 build/test run and the cross-build job also succeeds. Any kernel capability that is unavailable must remain an explicit skip rather than being silently counted as passed.
