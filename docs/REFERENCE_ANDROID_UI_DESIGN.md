# Reference Notes — Android UI Design Basics (2014)

Source: Francesco Azzola, *Android UI Design Basics*. This is an older Android-specific teaching text. ENML uses it only for enduring UI architecture/performance lessons; Android Activities, Fragments, XML resource layout, Java listener APIs, API levels, Holo themes, drawable qualifiers, and application packaging are not ENML ABI requirements.

## Useful principles for ENML

### 1. Consistency through standard interaction patterns

The source emphasizes that a platform UI framework should give applications reusable controls and familiar navigation patterns so users do not have to relearn basic interaction in every application. It also distinguishes top-level navigation from detail/task views and assigns persistent actions a predictable location.

ENML implication: M3.2 should begin with a small semantic control/navigation vocabulary rather than a raw arbitrary drawing toolkit as the primary application UI API. Standard components should carry predictable behavior, focus/state and accessibility semantics while still allowing visual theming above the stable semantic contract.

### 2. Hierarchical composition, but keep trees simple

The source models UI as a hierarchy of views and containers, and explicitly warns that increasingly complex hierarchies cost rendering time. It also notes that a simpler interface improves user experience.

ENML implication: the semantic UI tree should be hierarchical but bounded. Layout traversal, invalidation and accessibility traversal must have explicit node/depth/child limits. The framework should discourage unnecessary wrapper nodes and measure layout/render cost rather than assuming composition is free.

### 3. Responsive recomposition rather than fixed-pixel UI

The source repeatedly distinguishes physical screen size, pixel density and orientation. It recommends density-independent dimensions and different compositions for phone/tablet-sized screens; its list/detail example becomes separate screens on a phone and simultaneous panes on a larger screen.

ENML implication: M3.2 layout units should be logical/density-independent, derived from trusted display metrics rather than app-visible Linux pixels/device nodes. Responsive layout should be able to recompose the same semantic content into one-pane or multi-pane arrangements without requiring different application identities or rendering backends.

### 4. Reusable semantic subtrees and decoupled communication

The Fragment discussion treats a reusable UI piece as having its own lifecycle and recommends routing cross-component communication through an owning coordinator instead of tightly coupling sibling fragments.

ENML implication: do not copy Android Fragment lifecycle. Instead, use reusable semantic component subtrees with explicit ownership/lifetime and typed events. Sibling components should communicate through application state/controllers rather than obtaining ambient references to each other or to compositor internals.

### 5. Event/callback semantics belong to controls, not pixels

The source treats user interaction as events generated by UI objects and handled through listeners/callbacks. It also identifies focus, visibility and component state as shared view properties.

ENML implication: input routing should target semantic nodes/controls after trusted hit testing. Focus, enabled/disabled/selected/checked/pressed state and actions must exist independently of how pixels are drawn so accessibility, automation and secure UI can reason about them.

### 6. Separate structure/content from appearance

The styles/themes chapters argue against hard-coded visual values in each view and recommend separating UI structure from appearance, reusing style definitions and externalized resources.

ENML implication: the semantic tree should contain meaning/layout intent while a design-system/theme layer supplies typography, spacing, color, shape and motion tokens. Stable app ABI must not encode one ENML visual theme, and security state must not depend only on color/theme material.

### 7. Reuse work on scrolling/list UIs

The adapter/ViewHolder section explains that list rows should be recycled and repeated expensive lookup/inflation should be avoided to keep scrolling smooth.

ENML implication: later list/collection controls should use virtualization/recycling by construction. The platform should bound realized item count and avoid requiring every off-screen item to become a full rendered subtree. Accessibility still needs a semantic model for virtualized content rather than depending on currently allocated pixels.

### 8. Avoid blocking the interactive/UI path

The multimedia and remote-image sections warn against long blocking preparation/network work on the UI thread because it causes visible unresponsiveness.

ENML implication: M3.2 event/layout/render submission remains deterministic and bounded. Storage/network/media acquisition should be asynchronous service work with explicit completion/cancellation, not hidden synchronous I/O inside paint/layout callbacks.

### 9. Distinguish ordinary UI drawing from intensive graphics

The source distinguishes ordinary widget/custom-2D drawing from hardware-accelerated or graphics-intensive paths.

ENML implication: preserve the current architecture split. Most applications should use the semantic UI/rendering framework; future high-performance graphics APIs can be separate reviewed capabilities. Neither path should expose raw DRM/KMS/device-node authority.

## M3.2 acceptance direction derived from this source

M3.2 should prove at least:

- a bounded hierarchical semantic tree;
- standard control roles with explicit state and actions;
- logical/density-independent layout metrics;
- one-pane/two-pane responsive recomposition from the same semantic content;
- theme/style tokens separated from semantic structure;
- bounded list virtualization/reuse;
- explicit focus and event dispatch;
- accessibility information available without examining pixels;
- no blocking filesystem/network work in layout or event-dispatch hot paths;
- GCC, Clang, ASan/UBSan and native AArch64 gates.

## Do not copy

Do not reproduce Android Activity/Fragment lifecycle, Java listener classes, Android XML/resource directory conventions, API-level resource qualifiers, Intent routing, Holo/Android visual identity, Android drawable ABI, or NDK/OpenGL exposure merely because the source uses them. Those are examples from its platform and era, not ENML requirements.
