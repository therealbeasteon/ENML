# Reference notes — 2026-08-14: the QNX paper, read rather than cited

> **References teach principles. ENML determines implementation. External systems are not the design specification.**

## Why this note exists

`docs/M7_0_KERNEL.md` rests the entire case for writing a kernel on one number,
and that number comes from one reference:

> The measure of whether it was worth it is a single number: how many lines of
> code have to be trusted. If ENML's kernel reaches Linux's size, the exercise
> has failed regardless of what else it achieved.

The comparison it names is QNX: 605 lines for the microkernel, 15,930 for the
whole operating system. `.github/scripts/kernel-line-count.sh` has printed a gap
against those figures on every CI run since M7.10.

The source is `qnx-paper92.pdf` — Dan Hildebrand, *An Architectural Overview of
QNX*, Quantum Software Systems, 1992. It had been cited but not read. Reading it
found the comparison wrong in two independent directions, one flattering QNX and
one flattering Cookie. Both are now corrected in the script and in
`docs/M7_10_LINE_COUNT.md`.

## What the paper actually says

**1. The numbers are semicolon counts, not line counts.** The paper states its
own method in the sentence introducing the table: all of its source line counts
"were generated by counting the semicolons in the C source files."

Cookie's gate counts non-blank, non-comment lines. These are different
quantities and they do not differ by a constant. Measured both ways on the same
stripped text, Cookie's `core` is 3,419 lines and 1,583 semicolons — a ratio of
0.46. A C or C++ function signature, an `if`, a `for`, an opening brace, a label
and a preprocessor directive all cost a line and no semicolon.

So the headline "core is 5.7× the QNX microkernel" was dividing lines by
semicolons. Like-for-like it is **2.6×**.

**2. The 605-line microkernel does not contain memory management.** The paper is
explicit about scope: the microkernel implements four services — interprocess
communication, low-level network communication, process scheduling, and
interrupt dispatching — reached through 14 kernel calls.

Memory management is not among them. It lives in `Proc`, described as the first
and only mandatory resource manager, which "provides services such as process
creation, process accounting, memory management, process environment
inheritance… and pathname space management." `Proc` is 3,924 semicolons — six
times the microkernel — and it is a **user-space process**.

## What follows for Cookie, in both directions

**This is not headroom, and the ceilings did not move.** The ratchet in
`kernel-line-count.sh` measures Cookie against its own past, in one metric, and
that job never depended on what QNX counted. Every ceiling is unchanged by this
note. What changes is only what the project is entitled to claim.

**In Cookie's favour, on metric.** The gap has been overstated by roughly a
factor of two for as long as it has been printed.

**In Cookie's favour, on scope.** M7.11 is putting memory management *inside*
Cookie's kernel. QNX put it outside. From M7.11 onward, 605 is not the
comparable figure for a kernel that contains a VM subsystem; 605 + `Proc` =
4,529 is the honest comparison for that scope. Cookie's entire trusted image is
currently 3,924 semicolons.

**Against Cookie, and printed for that reason.** QNX's microkernel carries
low-level network communication, which Cookie's `core` does not and will not —
Cookie's networking is a service. Some of the 605 buys something Cookie's number
does not include, and the gap line says so rather than quietly taking the credit.

**Two things this does not license.** It does not make Cookie's kernel smaller;
it is the same code, measured the way the reference measured its own. And it
does not retire the M7.0 claim's teeth: 2.6× a 1992 realtime microkernel, for a
kernel that cannot yet mount anything and has no drivers, is still a number that
has to be defended rather than celebrated.

## The decision this settles

`docs/M7_11_MEMORY.md` left an open question and said it should be decided
before the code was written:

> **How much line count this costs, and whether that is acceptable.** … it is
> entirely plausible this milestone pushes `core` past 4,000.

That question was posed against 605 — a figure in a different metric that
excludes exactly the subsystem being added. The answer is not "M7.11 gets a
pass". It is that **the threshold was never 605 for this scope**, and the real
constraint is the ratchet, which is unchanged and which M7.11 has so far not
touched at all: three increments in, `core` has not moved a line.

## Method note, for whoever checks this

The semicolon count is produced by the same comment-stripping pass in
`kernel-line-count.sh` that produces the line count, so the two numbers describe
identical text and cannot drift. Two known imprecisions, stated rather than
buried:

- The stripper is lexical and does not track string literals, so a `;` inside a
  string literal would be counted. There is no such literal in the kernel today.
- Assembly sources contribute lines and almost no semicolons. This is
  *consistent* with the paper, which counted "the C source files" and so
  excluded QNX's own assembly, but it means the semicolon figure understates
  `machine` and `entry` relative to their real content. `core` — the number
  actually compared against 605 — contains no assembly, so the headline
  comparison is unaffected.

## Not adopted

QNX's architecture is not a template for Cookie and this note imports none of
it. The pathname-space/prefix-tree model, the `Proc`-owns-the-root arrangement,
network-transparent IPC as a kernel service, and the resource-manager API are
all outside ENML's design, which keeps typed bounded IPC, capability addressing
and trusted policy in its own shape. What is taken is a measurement method and
an honest statement of what a comparable number contains.
