# M4.10h — Profile-encrypted Storage

## Purpose

M4.10g gives Cookie a real profile-root destruction primitive, but cryptographic erasure is only meaningful when every protected durable byte is encrypted beneath that profile domain. M4.10h begins that storage half without weakening the existing descriptor-rooted confinement model.

References teach properties; Cookie owns the implementation. NIST media-sanitization/cryptographic-erasure guidance, FIPS AES guidance, Android file-based encryption, Apple Data Protection/effaceable-storage material, BitLocker key-separation material, and the project-supplied mobile-key references guide this design. Their ABI, keybag, filesystem layout, daemon topology, and vendor formats are not imported.

## Security contract

1. Protected user data is authenticated-encrypted before durable publication.
2. Bulk file data is never encrypted directly with the long-lived profile root.
3. A stable service-owned object identity, not a pathname, is cryptographic identity.
4. Every encrypted chunk authenticates at least crypto-format version, UserId, object identity, chunk index, plaintext length, and reserved flags.
5. Cross-profile, cross-object, and cross-chunk ciphertext substitution must fail authentication.
6. Nonces are generated by the trusted crypto provider. Callers never select or persist their own nonce policy.
7. Renaming a file does not require re-encryption and does not alter the cryptographic object identity.
8. Atomic replacement publishes only a fully authenticated new object generation; partial ciphertext never becomes the live file.
9. Temporary files, journals, caches, thumbnails, indexes, and other persistent derivatives containing protected data must be in the protected domain or explicitly prohibited.
10. Profile destruction must remove the key authority needed to decrypt every protected object and must not leave a recovery or backup key that silently restores the destroyed domain.

## Format slice implemented here

`ProtectedChunkHeaderV1` is encoded canonically as 52 bytes and is intended to be passed verbatim as AEAD associated data. The C++ object layout is never serialized.

Fields:

- magic / format version / header size
- `CryptoProfileId`
- durable `UserId`
- 128-bit `ProtectedObjectId`
- 64-bit chunk index
- plaintext length
- reserved flags, currently required to be zero

The current plaintext chunk ceiling is 48 KiB, fitting comfortably below existing bounded Storage/IPC limits while leaving space for the encrypted envelope. This number is a format/resource ceiling, not a filesystem block-size claim.

## Why paths are not authenticated identity

Paths describe namespace placement and are mutable through rename. Binding ciphertext to a pathname would either force re-encryption on rename or require an exception that weakens authentication semantics. Cookie instead gives the protected object a stable random identity and authenticates that identity on every chunk. Namespace metadata may separately bind a path entry to that object identity.

## Key hierarchy direction

The target hierarchy is:

`profile root -> Storage protection root -> object/file key -> authenticated chunks`

The profile root is authority, not a bulk-data cipher key. Object keys are disposable descendants and may be rotated or destroyed independently. A future slice will add a dedicated Storage key purpose/provider operation rather than reusing application-owned data-key authority.

## Algorithms

The current format accepts Cookie's versioned `aes_256_gcm_v1` profile. The identifier is part of authenticated metadata so a later reviewed profile can coexist without silently reinterpreting ciphertext. Algorithm selection is trusted system policy, not application input.

Post-quantum KEM/signature algorithms and ring signatures do not belong in this storage-data path: they solve key-establishment, signing, or anonymity problems rather than local bulk-data encryption. Package/update signing remains a separate trust domain.

## Exit criteria before claiming profile cryptographic erasure

M4.10h is not complete until all of the following exist and pass negative tests:

- a profile Storage protection root under the destructible hierarchy;
- provider-generated per-object/file encryption keys;
- AEAD seal/open for bounded chunks using the canonical header as AAD;
- service-owned random `ProtectedObjectId` generation with collision handling;
- encrypted atomic replace and crash recovery;
- authenticated namespace/object metadata sufficient to reject substitution;
- encrypted persistent service metadata and derivatives;
- revocation of live file/object capabilities when destruction begins;
- rollback-resistant `destruction_pending` state before key destruction;
- power-loss tests at every destruction transition;
- production effaceable-key hardware before any forensic-erasure assurance above logical destruction is advertised.

Until those criteria are met, Cookie must say that the mechanism is under construction rather than claiming complete forensic sanitization.
